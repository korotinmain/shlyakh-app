# Sky data: ADR 0009 and the bundled route asset (constellation path, plan 1 of 7) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A committed, license-clean asset with the 16 route constellations (stars, positions, magnitudes, lines, lighting order) built reproducibly from pinned d3-celestial sources, plus ADR 0009 and the attribution on the licences page.

**Architecture:** A Dart command-line tool in `tool/sky/` downloads d3-celestial files at a pinned commit, matches every figure vertex to a catalogue star (HIP id, magnitude), projects each constellation to a unit box, derives a deterministic lighting order and writes `assets/sky/route.json` and `assets/sky/SOURCES.md`. Pure functions live in `tool/sky/lib/` and are unit-tested with small fixtures; the app does not read the asset yet (plan 2 adds the domain loader).

**Tech Stack:** Dart (`dart:io` `HttpClient`, `dart:convert`, `dart:math`), flutter_test, no new dependencies.

**Spec:** `docs/superpowers/specs/2026-09-28-constellation-path-design.md` (Data and licences; Numbers; Decisions → Main route, After the main route, Shared stars).

## Global Constraints

- Sources: d3-celestial by Olaf Frohn, BSD-3-Clause, files `data/constellations.lines.json`, `data/stars.6.json`, `data/starnames.json`, fetched from `https://raw.githubusercontent.com/ofrohn/d3-celestial/<sha>/…` at one pinned commit SHA (look it up once with `gh api repos/ofrohn/d3-celestial/commits/master --jq .sha`, then hard-code it in the tool). Figures credited to "IAU and Sky & Telescope (CC BY 4.0)"; star data credited to XHIP (Anderson & Francis 2012).
- Do not bundle HYG or Stellarium data (CC BY-SA).
- Raw downloads are not committed (cache under `.dart_tool/sky/`); the generated asset, `SOURCES.md` and the tool are committed.
- Route order (IAU ids): main `Sge, Vul, Cyg, Lac, Cep, Cas, Per, Aur, Tau, Gem, Ori, Mon, CMa`; branch `Aql, Sct, Sgr`.
- Expected star counts (d3 figures, before shared-star resolution): Sge 4, Vul 5, Cyg 9, Lac 9, Cep 10, Cas 5, Per 23, Aur 9, Tau 12, Gem 12, Ori 23, Mon 9, CMa 11, Aql 8, Sct 4, Sgr 25. If the pinned data differs, stop and report — do not adjust the tool to match.
- Deterministic output: the same sources give byte-identical `route.json` (sorted keys, fixed decimals).
- No user-facing text in the asset (names are l10n keys in plan 2); the asset carries ids and HIP numbers only.
- Tests run with `TZ=Europe/Kyiv`; Pigeon before build_runner.

## Review Focus

- A figure vertex with no catalogue star within tolerance → the build fails naming the constellation and coordinate (never a silent guess). Tested in Task 2.
- RA wrap-around (d3 stores longitudes −180…180, a figure straddling 0h such as Cassiopeia/Pegasus side, or Pisces) → projection keeps the figure contiguous, not split across the box. Tested in Task 2.
- Two figure vertices matching the same star (repeated vertex in several polylines) → one star, lines reference it. Tested in Task 2.
- Elnath (β Tau) in both Auriga and Taurus → present in both constellations' star lists with the same HIP; resolution happens in plan 2, but the asset marks nothing extra. Tested in Task 4.
- Re-running the tool with no source change → no diff in `assets/sky/`. Tested in Task 3.

### Task 2: Pure sky functions with fixtures

**Files:**
- Create: `tool/sky/lib/sky.dart` (pure code), `tool/sky/test_fixtures/` (tiny JSON: two constellations, eight stars)
- Test: `test/tool/sky/sky_test.dart`

**Interfaces:**
- Produces:
  - `typedef SkyStar = ({int hip, double ra, double dec, double mag});` — `ra` in degrees 0–360, `dec` in degrees.
  - `Map<String, List<List<(double, double)>>> parseFigures(String geoJson)` — constellation id → polylines of (lon, lat) as d3 stores them.
  - `List<SkyStar> parseStars(String geoJson)` — from `stars.6.json` features (`id` = HIP, `properties.mag`, `geometry.coordinates` [lon, lat]); lon converted to `ra = lon < 0 ? lon + 360 : lon`.
  - `SkyStar matchStar((double, double) vertex, List<SkyStar> stars, {double toleranceDeg = 0.05})` — nearest star by angular distance; throws `StateError('no star within …° of (ra, dec)')`.
  - `typedef Figure = ({List<SkyStar> stars, List<(int, int)> lines, List<int> lightingOrder});` — `lines` index into `stars`; `lightingOrder` is star indices in the order they first appear walking the polylines as stored.
  - `Figure buildFigure(List<List<(double, double)>> polylines, List<SkyStar> catalogue)` — dedupes stars by HIP, keeps every segment once (unordered pair), no self-segments.
  - `List<(double, double)> project(List<SkyStar> stars)` — gnomonic projection around the figure's centre (mean of unit vectors), north up, east to the LEFT (as seen on the sky), scaled uniformly so the larger side spans [0, 1] and the smaller is centred; values rounded to 4 decimals.

- [ ] **Step 1: Failing tests** with the fixture: `parseFigures` returns both ids and their polylines; `parseStars` converts lon −10 to ra 350; `matchStar` finds a star 0.01° away and throws for 1° away; `buildFigure` on a polyline A-B-C plus a second polyline B-D gives stars [A, B, C, D], lines {(0,1),(1,2),(1,3)}, lighting order [0,1,2,3]; a repeated vertex yields one star; `project` keeps a figure at ra 359° and 1° contiguous (x distance ≈ small, not ≈ 1), puts the eastern star on the left, and all coordinates are in [0, 1].
